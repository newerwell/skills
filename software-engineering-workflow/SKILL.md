# 工程化写代码

让代码的行为能用例子说明，变更能被独立审查，验证结果能被复现。根据项目寿命、改动影响和回退成本选择实践，优先沿用仓库已有的约定、命令和工具。使用 AI 时，把仓库里的实现当成 Agent 会照着写的示例，优先让正确做法容易找到、错误做法能被工具发现。

## 按请求选择工作方式

- **学习或解释。** 围绕用户的问题解释一个工程取舍，用具体例子说明它何时有用。用户需要出处或延伸阅读时，从[阅读资料](references/reading.md)选对应条目。
- **审查或评价。** 对照需求看设计、行为、复杂度和测试有效性，按影响列出发现。已复现的问题给出最短操作、实际结果和预期结果。从代码直接推出的问题给出输入与调用路径。依赖未知配置、数据或时序的推测标为待验证，写清哪一次观察能判定。只要求审查时，以审查意见收尾。
- **实现、修复或重构。** 从正常入口确认预期行为，再按下列流程修改和验证。用户同时要求审查和修复时，用审查发现界定改动范围。

## 实现任务的工作流程

1. **定义预期行为。** 找到现有入口和调用方，把需求写成「给定条件 → 执行动作 → 可观察结果」，列出会影响实现的边界和失败场景。改动数据或接口前，确认旧数据和调用方应如何继续工作。修复重要缺陷时尽量先复现，做性能优化时先记录基线和测量条件。
   偶发或跨模块故障的原因不清时，沿同一次操作核对各层的输入、输出或状态。有正常样本时，对照两条路径最早出现差异的位置。提出一个可能原因，用能排除该原因的检查来验证。暂时无法复现时，指出下次故障需要捕捉的具体证据。
2. **划清代码职责。** 找到对这条规则负责的模块。业务判断放在能单独验证的位置，网络、数据库和文件操作放在明确的边界。用实际需求判断是否需要新接口或抽象。用命名表达用途，用注释记录代码本身难以表达的原因。
3. **按目的切小改动。** 每次变更解决一个可说明的问题，带上使用入口、相关测试和必要说明。将独立的结构整理与行为变更分开。拆出的每一步应能独立理解和验证，并保持项目可用。
4. **按风险验证行为。** 先运行快、稳定、范围小的检查，再通过必要的集成或端到端验证覆盖真实的交互边界。断言应反映用户或调用方能观察到的结果。需要重复验证关键流程时，按下面的方法记录真实运行步骤。
5. **交付改动与证据。** 说明验收条件、实际运行的命令或操作、验证环境、结果和仍待验证的路径。团队项目用 CI 频繁验证集成后的构建与测试，并及时处理主线失败。运行方式变化时，同步更新依赖、配置和启动说明。涉及部署、数据迁移或外部副作用时，按影响验证兼容性和恢复方法。

## 把 Agent 的重复错误变成自动反馈

从重复出现的审查意见、回滚或用户纠正里找出实际错误。选择能解决问题的最简单方式：

| 方式 | 什么时候用 |
| --- | --- |
| 代码结构和 API | 能通过一个明确的调用入口消除错误选项时，收拢职责，按范围迁移或移除容易被模仿的旧写法 |
| 类型和 lint | 结构仍允许错误，但能静态识别时，让不合法的状态或依赖关系直接报错，并指出正确入口 |
| 行为测试 | 错误体现在输入、输出、状态变化或副作用上时，用断言捕捉实际差异 |
| `AGENTS.md` 或 Skill | 需要人或 Agent 根据场景作判断时，用文字说明取舍和例子 |

先确认新增检查能拦住一个已知错误，再确认正确实现能通过。历史问题较多时，可以先阻止新问题进入，再清理旧示例。如果结构调整超出当前任务，留下错误样例和改进建议。

## 按风险选择验证

| 改动 | 优先检查 | 何时扩大范围 |
| --- | --- | --- |
| 文案、样式或其他低风险改动 | 检查直接受影响的页面、输出或现有命令 | 影响多个入口或共享组件时，检查有代表性的调用方 |
| 业务规则、状态转换 | 用单元或组件测试覆盖典型路径、边界输入和错误结果 | 数据持久化或调用顺序影响结果时，覆盖相应集成边界 |
| 数据库、网络或外部 API | 用集成或契约测试检查数据、错误和超时如何跨边界传递 | 关键结果取决于真实依赖时，再用对应环境验证 |
| 旧数据、迁移或升级兼容 | 从上一版本留下的样本开始，用新版入口操作，再读回历史记录与关键字段 | 风险涉及进程重启、并发重试或恢复时，按对应使用方式复查 |
| 关键用户流程或发布行为 | 用少量端到端检查覆盖有代表性的完整流程 | 不可逆数据变更或重要发布风险需要单独验证恢复与回退 |

**验证收尾条件。** 当前版本已通过项目要求的检查，且验证结果覆盖本次验收条件和主要风险时，即可交付。只有后续改动、检查失败或具体的覆盖疑点才需要重跑或扩大检查。必要检查因环境受阻时，说明已经验证的部分、受阻原因，以及还缺哪项证据。

## 让 Agent 通过真实入口验收

优先复用现有启动命令、浏览器测试、CLI 或 API 验证脚本。对反复验证的关键流程，维护一份简短的功能地图，记录以下信息：

- **准备。** 使用哪个版本和环境，如何启动，什么信号表明应用已可用，需要哪些测试数据。
- **操作。** 用户走哪个入口，如何用稳定的选择器、命令或 API 执行同样的操作。
- **断言和证据。** 检查用户动作和动作后的状态。有持久化写入时，从另一次读取核对结果。测升级兼容性时，可用旧版生成的样本，或按已确认的旧表结构构造小型数据库。记录样本来源、复查命令和结果，再清理临时数据。

截图适合展示界面状态，交互应通过明确操作和断言验证。使用模拟依赖时，写清验证覆盖的边界和仍待实测的路径。对于复杂的并发或状态转换，可以先用状态图说明允许的变化，再决定是否值得做属性测试或模型检查。

## 多个 Agent 协作时

先让单个 Agent 能重复完成「定位 → 修改 → 验证」。任务相互独立、各自有明确的验收方式，且分工有实际收益时，再扩大并行。合并前用相关检查验证待合并的版本。人工审查聚焦需求取舍、验证覆盖缺口和高风险改动。

## 示例：订单状态筛选漏单

订单列表每页两条，按 ID 升序排列。准备三笔订单，101 和 102 已完成，103 已取消。用户选择「已取消」后，第一页应出现 103。清空筛选后，第一页应恢复为 101 和 102。

1. 在查询层写下第一页必须返回 `[103]` 的断言。先分页再筛选会先取 101、102，最后返回空列表。用旧实现运行该检查，确认它能捕捉漏单。
2. 把状态筛选放到分页之前，沿用已有的排序和分页逻辑。用同一批数据、同一条断言验证修复。
3. 通过订单页面选择并清空筛选，核对两次显示的订单 ID。记录实际验证的环境与结果。保留查询测试，后续改动一旦恢复旧顺序就会触发失败。

# 工程化写代码

让代码的行为能用例子说明，变更能被独立审查，验证结果能被复现。根据项目预期寿命、改动影响和回退成本选择实践。优先沿用仓库已有的约定、命令和工具。

## 从需求走到交付

1. **定义预期行为。** 找到现有入口和调用方。把需求写成「给定条件 → 执行动作 → 可观察结果」。列出会改变实现的边界和失败场景。改动数据或接口前，确认已有数据和调用方应如何继续工作。
2. **划清变化的位置。** 找到应承担这条规则的模块。把业务判断放在能单独验证的位置，把网络、数据库和文件操作放在明确的边界。用实际需求判断是否需要新接口或抽象。给代码和测试起能表达用途的名字，注释记录实现本身难以表达的原因。
3. **按目的切小改动。** 每次变更解决一个可说明的问题。连同使用入口、相关测试和必要说明一起交付。将独立的结构整理与行为变更分开，便于看出影响和回退。拆开的每一步应能独立理解并保持项目可用。
4. **验证最值得担心的行为。** 优先用快、稳定、范围小的检查获得反馈，再用必要的集成或端到端检查覆盖真实接缝。修复重要缺陷时，尽量先用一个可重复的检查捕捉问题。检查的断言应能反映用户或调用方可观察的结果。
5. **把交付和证据一起留下。** 通过仓库现有命令运行相关检查，记录结果和验证环境。团队项目用 CI 频繁验证集成后的构建与测试，发现主线失败时及时处理。涉及运行方式变更时，更新依赖、配置和启动说明。涉及部署、数据迁移或外部副作用时，按实际影响验证兼容性、回退或恢复办法。

## 按风险选择验证

| 改动 | 优先检查 | 何时扩大范围 |
| --- | --- | --- |
| 文案、样式或其他低风险改动 | 检查直接受影响的页面、输出或现有命令 | 影响多个入口或共享组件时，检查有代表性的调用方 |
| 业务规则、状态转换 | 用单元或组件测试覆盖典型路径、边界输入和错误结果 | 数据持久化或调用顺序影响结果时，覆盖相应集成边界 |
| 数据库、网络或外部 API | 用集成或契约测试检查数据、错误和超时如何跨边界传递 | 关键结果取决于真实依赖时，再用对应环境验证 |
| 关键用户流程或发布行为 | 用少量端到端检查覆盖有代表性的完整流程 | 不可逆数据变更或重要发布风险需要单独验证恢复与回退 |

做审查时，以设计、行为、复杂度和测试有效性为主。指出具体问题、触发条件和影响，说明如何验证。做实现时，交付结果应说明改了什么、跑了哪些检查、哪些关键路径仍待验证。替身或模拟测试通过，只能证明这些测试覆盖的行为。

## 示例：给订单列表增加状态筛选

- **行为**：选择「已取消」时，只展示已取消订单。清空筛选时恢复现有列表。旧链接不带筛选参数时沿用原有行为。
- **边界**：集中处理状态参数的解析与校验，数据库查询先应用筛选再分页。页面负责展示筛选项与空结果。
- **验证**：用单元测试检查有效、缺省和非法参数。用集成测试检查混合状态数据下的结果和分页。用一条页面验证覆盖选择与清空筛选。
- **交付**：把该入口的行为和相关测试放在同一变更。记录运行过的检查和结果，明确页面验证是在本地、测试环境还是线上完成的。

## 阅读资料

当用户想理解某条实践的原因或索要出处时，使用下列资料。初学时可依次读 Google 的软件工程导论、代码审查指南、测试金字塔和持续集成。

- **软件工程导论，Titus Winters。** 从时间、规模和取舍理解软件维护。代码的预期使用时间越长，越需要保留适应需求、环境和依赖变化的能力。[What Is Software Engineering?](https://abseil.io/resources/swe-book/html/ch01.html)
- **代码审查，Google。** 先检查设计、行为和必要复杂度，再看测试、命名、注释和文档。检查代码出错时相关测试是否真能失败。[What to Look for in a Code Review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)
- **小改动，Google。** 一次审查围绕一个自包含的目的展开，带上理解这个改动所需的上下文和相关测试。不同变更的合理大小由依赖和审查难度决定。[Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)
- **推迟推测性功能，Martin Fowler。** 预先实现猜测中的需求会增加当前复杂度和维护成本。自动化测试与重构让未来真的需要修改时更容易下手。[YAGNI](https://martinfowler.com/bliki/Yagni.html)
- **测试分层，Ham Vocke。** 让不同粒度的测试各自解答一个问题。把多数断言放到快速、范围小的层级，通过较少的高层检查验证关键流程。[The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- **持续集成，Martin Fowler。** 频繁合入主线，用自动构建和测试检验每次集成，及时处理失败以缩短反馈时间。[Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html)
- **服务运行与交付，Adam Wiggins。** 显式声明依赖，从运行环境读取部署配置，区分构建、发布和运行，尽量缩小环境差异。适用于需要部署的 Web 或 SaaS 服务。[The Twelve-Factor App（简体中文）](https://12factor.net/zh_cn/)
